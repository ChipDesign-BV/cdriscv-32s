# cdriscv-32s safety manual (draft)

> **Status: not verified yet — do not use yet.**
>
> This document is a *draft outline* of a safety manual. The IP has not
> been verified, no FMEDA has been performed, no diagnostic coverage has
> been measured and no fault injection campaign has been run. No claim
> of compliance with ISO 26262, IEC 61508 or any other functional safety
> standard is made, and none may be derived from this document. It
> records design intent so that a real safety case can later be built,
> or shown to be unachievable.

## 1. Intended use

`cdriscv-32s` is intended as the digital control element of a
mixed-signal SoC where a failure of the control loop has to be detected
and signalled to a system-level safety mechanism within a short fault
tolerant time interval. It is a *safety element out of context*: the
integrator owns the item definition, the hazard analysis and the
allocation of requirements.

The subsystem is designed to be **fail-silent with external
notification**: it detects a fault, latches it, optionally resets
itself, and signals the outside world on `err_pin_o`. It does not
continue operating through a fault, and it has no redundant channel that
could take over.

## 2. Safety mechanisms and what they cover

| # | Mechanism | Covers | Reaction |
|---|-----------|--------|----------|
| SM1 | Dual core lockstep with `LockstepDly` cycle delay | permanent and transient faults in core logic | fault bit 0 |
| | *measured*: a fault on a compared signal is detected in 2 cycles. A fault on the **register write port may never be detected**: it is not compared, so it is only caught if the corrupted value later reaches an address, a branch or a store, and a dead register write is invisible. Measured undetected after 20 000 cycles. An earlier figure of "2 cycles" here was an artefact of test timing and has been withdrawn — see finding V4-F3 | | |
| SM2 | SEC-DED on the I-TCM and D-TCM | single bit errors (corrected), double bit errors (detected) | fault bits 1..4, bus error on uncorrectable |
| SM3 | Odd parity on the register file | single bit errors in architectural registers | fault bit 5 |
| SM4 | March C- memory BIST on the raw code words | memory manufacturing and latent faults | fault bit 9 |
| SM5 | Windowed watchdog with key sequence | program flow failure, servicing too early or too late | fault bit 6, optional reset |
| SM6 | Clock monitor in an independent clock domain | loss of clock, frequency out of range | fault bit 7 |
| | *measured*: a stopped system clock, a 1.5x slow clock and a 2.5x fast clock are all detected; no false trip at the nominal ratio | | |
| SM7 | Bus error responder on unmapped addresses | runaway program counter, wild pointers | fault bit 8, precise trap |
| SM8 | ADC result range check, conversion time-out, analog flag inputs | failure of the analog domain | fault bit 10 |
| SM9 | Trap reporting to the safety controller | unexpected illegal instruction | fault bit 12 |
| SM10 | Fault injection (`SELFTEST`, TCM injection, comparator injection) | latent faults in SM1 and SM2 themselves | proves the detection path |

## 3. Assumptions of use

The integrator must satisfy all of the following. None has been
validated.

* **AoU-1** `ref_clk_i` is generated by an oscillator that is
  independent of the source of `clk_i`, otherwise SM6 cannot detect a
  common clock failure.
* **AoU-2** `err_pin_o` is monitored by an external device that puts the
  system into its safe state. In toggle mode the monitor must check
  both edges and a maximum period.
* **AoU-3** The software configures the safety controller (`ENABLE`,
  `REACT_*`, `CTRL`) and sets `CTRL.lock` before enabling any actuator.
* **AoU-4** The software configures and locks the watchdog and services
  it only from the intended point in the control loop.
* **AoU-5** The memory BIST is run before the application image is
  loaded, either through `MbistAuto` or from a boot routine that touches
  neither TCM. This is not only a test: **every TCM word must be
  written before the core is released**, because the instruction
  prefetcher fetches past the end of the program and an unwritten word
  holds an arbitrary pattern that the SEC-DED check will most likely
  call an uncorrectable error. The BIST leaves the memory at the
  all-zero code word, which is a valid one, and so satisfies both
  requirements at once. An image loader that writes only the program
  must zero the rest. See finding V4-F2.
* **AoU-6** The application periodically executes the fault injection
  self tests (SM10) to bound the latent fault metric of SM1 and SM2.
* **AoU-7** Corrected single bit errors (fault bits 1, 3) are counted by
  the software; a rising rate indicates a memory that is degrading.
* **AoU-8** The two TCM instances and the two cores are placed so that a
  single physical defect or a localised disturbance cannot affect both.
  Common cause failure of the lockstep pair is *not* covered by any
  mechanism in this IP.
* **AoU-9** Scan chains, if inserted, must not create a path that
  bypasses the lockstep comparator in functional mode.
* **AoU-10** The subsystem has no protection against malicious software:
  privilege separation, PMP and memory protection are not implemented.

## 4. Fault reaction

1. A mechanism reports a fault for at least one cycle.
2. The safety controller latches it in `STATUS` if `ENABLE` allows.
3. Per source, the reaction is any combination of: safety interrupt,
   warm reset request, external error pin. The reset request is a pulse
   per latched fault, not a level: a level would hold the core in reset
   for ever, since only software can clear the sticky status and the
   software would never run again (finding V7-F1).
4. The warm reset restarts the core and the bus, and leaves the
   peripherals and their status registers standing so that the software
   can determine the cause after the restart.

Uncorrectable memory errors additionally produce a precise trap on the
accessing instruction (load/store access fault, or instruction access
fault on a fetch).

## 5. Known gaps

These are known and unresolved. They are the reason the IP must not be
used yet.

* No FMEDA, no diagnostic coverage figures, no single point fault
  metric, no latent fault metric.
* A fault injection campaign has been run: 3 000 single event upsets
  over a named list of nine state elements, across three workloads. No
  silent data corruption and no hangs; 41 % detected on the arithmetic
  workload, 57 % on the trap and interrupt one, 43 % on the memory
  one. This is not a diagnostic coverage figure and must not be quoted
  as one: the fault list is nine elements rather than the flop list,
  and the spread between the two workloads is the point — detection
  depends on what the software makes live, so any figure quoted has to
  name the workload it was measured on. See `verification_findings.md`,
  phase V9.
* No gate level fault injection.
* The lockstep comparator itself is single point: a fault in the
  comparator can mask a core fault. Only the injection self test bounds
  this, and only if the software runs it. The self test is now known to
  work: `make safety` exercises it.
* A register file fault may be **undetected indefinitely**, not merely
  detected late (finding V4-F3): the lockstep compare vector does not
  carry the register write port, and a corrupted value that is never
  read again never reaches a compared signal. The FTTI argument cannot
  rest on indirect detection. Adding `rd_addr` and `rf_wdata` to the
  compare vector — 37 bits — makes detection unconditional and single
  cycle, and is the recommended resolution.
* The safety controller's status registers are not themselves protected
  by ECC or parity.
* The bus interconnect is not protected: address and data are unprotected
  between the core and the memories; only the memory contents are covered.
* No end-to-end protection of the ADC data path beyond the range check.
* Timing constraints, CDC constraints and lint waivers are not written.
* No verification of any kind has been performed. See
  `verification_plan.md`.
